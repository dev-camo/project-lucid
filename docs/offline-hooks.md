# Offline hook registry

Every point where the offline adapters (namespace `ProjectLucid.Offline`) divert an original member. Decision D2: a hook is a check of the central switch `ProjectLucid.Offline.OfflineAdapters.Active` (`Packages/com.hardlight.hlunitycore/Runtime/Offline/OfflineAdapters.cs`) in the hooked method, with the original body kept verbatim after it, so the original is always compiled and its generated names stay exact. Three shapes are used. Most hooks are a guard at the top that runs the adapter and returns. Mid-method hooks (H-001, H-010, H-013, H-017, H-053, H-065, H-067..H-075) sit where the original diverges, after statements the original still runs first. Fall-through bookkeeping (H-031..H-037, H-039..H-042, H-064) does adapter work such as a stop check or remembering a manager, then continues into the original body. Each hook in source carries a comment `Offline hook H-nnn: ...`; search for `OfflineAdapters.Active` or `Offline hook` to find them all.

`tools/tests/test_offline_hooks.py` checks that this table and the source agree. Add a row here for every new hook, and never reuse an ID. Retired IDs: H-054 (`ChallengeLeaderboardIntegration_GameCenter.CanShowLeaderboard` reported whether the local records were ready; it now runs the original login query, which is false offline through H-052, so the challenge leaderboard button is disabled by the game's own `UIContainerChallengeLeaderboard` availability).

No `#if` is left for a hook. GameCenter cannot be used by this project at all (it requires App Store distribution), so every GameCenter and `Social` path is replaced by an offline adapter on every platform, macOS included: H-001..H-005, H-017, H-019..H-030, H-043..H-052. One platform guard remains, and it is not a hook: `UnityEngine.SocialPlatforms.GameCenter` exists only in Apple players, so in `Achievements.cs` and `LeaderboardManager.cs` the `using` directives and the three `GameCenterPlatform` calls are inside `#if UNITY_IOS || UNITY_TVOS || UNITY_STANDALONE_OSX`. They compile as shipped on macOS and are left out of Windows and Linux players, where offline hooks H-030, H-044 and H-050 keep them unreachable anyway. The original code compiles everywhere, including the seven unresolved native imports of H-011, H-058..H-061, H-062 and H-063, which are declared like Cloud_MacOS declares its imports (`[PreserveSig] static extern` with no recovered module, under `#pragma warning disable 0626`).

## Hidden cross-promotion entry points (H-077..H-079)

D14 hides the entry points rather than presenting an empty promotion page. The release asset inventory contains two launchers: `uicontainer_start_menu` and `uicontainer_level_results`. The start menu's content button targets its launcher. Level results has a separate `button_tertiary_more_games` button and `group_controller_more_games_prompt` input event targeting its launcher; its content button's legacy base-typed callback has a null target, and is hidden with the launcher parent. The level-results `ShowMoreGamesButton` bindings and visibility group can reactivate these separate owners, so the policy also applies on re-enable. Matching uses persistent target identity and the launch method, not object names. Button discovery includes inactive children but stops at nested UI-container ownership. Unrelated controls keep their original activity and callbacks.

H-057 still registers the real cross-promo system over the no-content resource manager without constructing a download manager or sending requests. H-065 still protects direct base-button updates with an empty ad list. The original launch actions, container, requirements and menu binders are unchanged and compiled. Disabling the central adapter switch restores the original enable paths, including controller subscriptions and cached-placeholder behavior.

## Windows and Linux players (H-070..H-076)

The release shipped one desktop player, for macOS, so its desktop behaviour sits behind `RuntimePlatform.OSXPlayer` checks. Offline, the Windows and Linux players take those macOS player branches (#503): each hook checks `OfflineAdapters.Active && OfflineDesktopPlatform.IsMacPlayerEquivalent`, which is true only on `WindowsPlayer` and `LinuxPlayer`. The editors keep their own branches, as in the original, and the macOS player runs the original checks. `OfflineDesktopPlatform.OverridePlatform` substitutes the player platform for tests only. Every runtime `OSXPlayer` and `OSXEditor` check was inventoried; these need no hook:
- `Achievements.cs` and `LeaderboardManager.cs`: the `#if UNITY_IOS || UNITY_TVOS || UNITY_STANDALONE_OSX` GameCenterPlatform guards, already unreachable offline (above).
- `DevicePerformance_iOS`/`_macOS`/`_tvOS.Platform`: the constants that key the device performance table, which H-072 reads.
- `UIContainerGameCenterAccessPoint.Start` glyph: an iOS and tvOS test, not a macOS one.
- Serialized platform lists other than the input monitors: the only `UIEventFromInput.m_ignoreOnPlatforms` entry is iOS, and the only `ControlMap` blocked-input row is tvOS, so neither names the macOS player.
- `LucidPlayerCompilation` (editor tooling, `OSXEditor` app bundle path) is not player code.

## Controller input (H-013, H-080..H-082)

The shipped `HLInputModule` (`s_apple`, `s_gui`) drives two monitors. `TouchInputMonitor` reads keyboard, mouse and touch through legacy `Input`, which works on every desktop player. `ApplePluginControllerInputMonitor` carries every gamepad binding, through the Game Controller framework, which exists only on Apple platforms. Its one authored binding (`Controller - ApplePluginBinding`) is forced, so every connected controller gets it, and its identifiers (`Xbox`, `DUALSHOCK`, `Wireless Controller` and others) pick the glyph set from the controller's vendor name.

The owner chose Unity Input System 1.x as the controller backend on macOS, Windows and Linux (#454). The original Apple controller classes stay restored and unchanged, and the original Game Controller path is unreachable offline:

- **Provider (H-013).** `InputSystemControllerProvider` (`Packages/com.hardlight.hlinput/Runtime/Offline/`) keeps the connected gamepads and their names in two parallel lists, and drops a controller from both when it disconnects, like the original `ApplePluginControllerProvider`. `BaseActiveBindings` passes a name's index to the binding as its joystick index and the sources index the device list with it, so binding, input and glyph always name the same device. Compacting is what the original Apple consumers saw: both original providers removed disconnected controllers.
- **Notifications.** The original polling compares only the count, so it never reported a controller replaced between two polls. The provider runs its own polling at the configured rate instead, and notifies once per poll after any connect or disconnect. Connect, disconnect and reconnect notify once, as in the original; an equal-length replacement or a swap now also notifies once; an unchanged poll does not notify.
- **Names.** DualShock 4 and DualSense pads report their macOS vendor names, which resolve to the PlayStation glyphs as on macOS. Xbox pads report Input System's own `Xbox Controller`: `BaseInputBinding.Setup` keeps the last identifier a name contains, and the macOS name `Xbox Wireless Controller` would end on `Wireless Controller` and show PlayStation glyphs. Other gamepads keep their own name and take the binding's fallback, as an unrecognised controller did on macOS.
- **Game Controller view (H-080..H-082).** `InputSystemGCControllers` (`Packages/com.hardlight.hlappleinput/Runtime/Offline/`) gives each connection one `GCController`, in the provider's order, so the original source, bindings, processors and button-down history run unchanged. The provider numbers every connect, also when Input System revives the same `Gamepad` object on reconnect, so a reconnected pad gets a new `GCController` with empty history, as the original service constructs one per connection (0x06000069, 0x06000052), while a refresh caused by another device keeps an uninterrupted controller and its history. There is one view per provider, like the original provider's own controller list. It registers its controllers' handles for polling and removes only its own registrations: when a controller disconnects, and when the provider stops, which empties both provider lists as the original `ApplePluginControllerProvider.Shutdown` does (0x06000015) and disconnects the view's controllers, so a pad that stays added is no longer polled through them. Polling reads the gamepad in Game Controller's layout: triggers are the back shoulders, Start is Menu, View/Share is Options, and each D-pad axis is read from its two buttons, so a diagonal is a full -1 or 1 on both axes as Game Controller reports it. There are no Game Controller symbols, so glyphs come from the authored glyph map.
- **No hook needed.** `App.ValidateHasAtLeastOneController` and `OnControllerConnectedButton.Start` test for `ApplePluginControllerProvider` and take their existing non-Apple branches (the check passes, the button stays inert), as they did with the earlier portable provider. `GCControllerService.Initialize`, `GetConnectedControllers` and `SetControllerLightColor` are reached only from `ApplePluginControllerProvider`, which is never created offline.
- **Project changes.** `com.unity.inputsystem` 1.11.2 (the version the Unity 2022.3.54 editor bundles) is added, with `activeInputHandler: 2` (both), so legacy `Input` keeps serving `TouchInputMonitor`. `HLInput.Runtime` and `HLAppleInput.Runtime` reference `Unity.InputSystem`; the adapters alias `UnityEngine.InputSystem.InputSystem`, because the game's own `HardlightProject.InputSystem` takes that name. The package is listed in `testables` so the EditMode tests can use its isolated test fixture.

## Local save storage (H-010)

H-010 swaps `HLSaveMethodEncrypted` for `LocalPropertySave` (`Packages/com.hardlight.hlunitycore/Runtime/Offline/LocalPropertySave.cs`, created by `OfflineProviders.CreatePropertyStorage`). `HLPropertyStore` is unchanged above the storage: the game still builds `new HLPropertyStore("H4RDl1ght_S4VE", 0, "Primary")` and loads the slot `HL_Default_Save_ID` at boot (`ApplicationStateBoot`).

- **Format.** The files are in `Application.persistentDataPath`, not encrypted. `HLPropertyStore.SavePropertyData` still builds the original text payload (client version line, property count line, then two lines per property); `LocalPropertySave.SaveData` wraps it in a UTF-8 JSON envelope written with `JsonUtility`: `formatVersion` (always 1), `payload` and `sha256`, the lowercase hex SHA-256 of the payload's UTF-8 bytes. A file is readable only if it parses, has `formatVersion` 1, a non-null payload and a matching checksum (`TryRead`).
- **Original saves.** The original `HLSaveMethodEncrypted` format (length-prefixed, encrypted) is not read or migrated. `LocalPropertySave` does not use the key argument. The original `HLSaveMethodEncrypted.GetFileName` builds the same names, so an original encrypted file copied into the local `persistentDataPath` is not ignored: `TryRead` rejects it, and if no readable copy exists boot stops as described under "Both copies unreadable". This does not happen normally, because this project's identity (and so `persistentDataPath`) differs from the original's.
- **File names.** The primary is `<file name><slot id>` (`Primary` + `HL_Default_Save_ID`); the backup adds the suffix `-backup`. File names and slot ids may not start with `.`, end in `-backup`, or contain characters below U+0020 or any of `<>:"/\|?*`. Helper files begin with `.`, so slot listing never mistakes them for slots.
- **Writing.** Each write goes to a `.tmp` file in the same directory, is flushed, then replaces the target with `File.Replace` (or `File.Move` for a new file); a failed write leaves the old file. Up to five attempts are made, as in the original. Before a primary write replaces an existing primary, a readable old primary becomes the `-backup` file; an unreadable old primary is kept as `.<primary name>.corrupt-<guid>` and does not replace the backup. `HLPropertyStore.SavePropertyData` then calls `BackupData`, which copies the new, readable primary over the backup, so after a successful save the backup matches the primary; the old primary survives as the backup only if `BackupData` fails. Deleting a slot (`WipeSaveFile`) removes the primary and backup only; `.corrupt-` files stay.
- **Loading.** `HLPropertyStore.LoadInternal` reads the primary, then the backup. If neither file exists, the slot is new and the store starts empty, as in the original. If a file exists but is unreadable, a readable backup is used.
- **Both copies unreadable.** If a primary or backup file exists and neither can be read, `LocalPropertySave.LoadData` throws `InvalidDataException("Local property save and backup are unreadable; both files were preserved.")`. This differs from the original `HLSaveMethodEncrypted.LoadData`, which catches read failures and returns null so the store starts a new save. Offline, neither file is erased or overwritten (the rule agreed in #85), so the next save cannot replace progress that might be recovered by hand.
- **Effect on boot.** The exception is thrown inside `HLPropertyStore.LoadInternal` after `m_currentState = State.Loading`, so the reset to `State.None` is skipped, and it propagates out of `ApplicationStateBoot` (`LoadFromIdentifier("HL_Default_Save_ID")` is not guarded). Boot stops there. No message is shown to the player. The store stays in `State.Loading`, so later loads return at once and `CanSave` is false. To recover, move the unreadable files out of `persistentDataPath` (or restore a good copy of either file) and restart.

## Game Center pages (H-026, H-027, H-050)

Offline, a request to show the Game Center achievements or leaderboard pages does nothing. The evidence and the decision:

- **The original's not-logged-in path.** `ApplicationStateOpenGameCenterPage` (only in `FSMApplication_SettingsMenu`) calls `GameCenter.ShowAchievementPage` or `ShowLeaderboardPage`, which call `Social.ShowAchievementsUI` and `Social.ShowLeaderboardUI`. On the shipped macOS player `ActivePlatform.SelectSocialPlatform` creates `GameCenterPlatform`. Its `ShowAchievementsUI` (0x06000066, x86-64 0x2711C60) and `ShowLeaderboardUI` (0x06000067, 0x2711D10) first call `VerifyAuthentication` (0x06000065, 0x27117B0), which logs "Must authenticate first" through `Debug.Log` and returns false when `localUser.authenticated` is false. The page is then not shown. The local profile is never logged in (H-020), so H-026 and H-027 take that path. The static `GameCenterPlatform.ShowLeaderboardUI(string, TimeScope)` (0x06000083, 0x2712340) behind H-050 has no such check and calls the native `ShowSpecificLeaderboardUI` directly, so H-050's no-op is a divergence.
- **The settings flow is unchanged.** `OnAchievementsOpen` and `OnLeaderboardsOpen` close `uicontaineridentifier_settings`, enter `OpenAchievementPage` or `OpenLeaderboardPage`, and leave at once through the `Always` transitions `WaitBehindAchievementsOverlay` and `WaitBehindLeaderboardsOverlay` back to `SettingsGroup`, which reopens settings. The request returns at once, so settings reopens as it did for a player who was not signed in.
- **Leaderboard buttons.** H-050 is reached from `UIContainerLeaderboards` (the mission select, bonus-zone mission select and level results containers) through `TimeTrialLeaderboardManager.ShowLeaderboard`, and from `UIContainerChallengeLeaderboard` (challenges overview) through `ChallengeManager.ShowLeaderboard`. The time-trial button does nothing. The challenge button is disabled by the game itself, because `CanShowLeaderboard` runs the original login query (H-054 retired).
- **Why not a replacement screen.** No shipped screen fits. The leaderboard container is two buttons that call the platform UI, `FSMApplication_LeaderboardsMenu` opens a container identifier that was never exported, and the ornament gallery's Achiever tab shows ornament unlocks and can be reached only from the main menu's Collections flow, which unloads the level. A new overlay cannot be made modal with the shipped input layer: `ControlMapping` filters by input, not by handler, with no priority and no way to consume an input. The settings menu's own back is an ungated `InputEvent` on `UIBack`, so a back press would reach both the overlay and settings. The owner therefore chose a no-op: with no Game Center there is no reason to keep the action, and a no-op leaks nothing.

Local achievement progress and personal records are still stored (`LocalAchievementRuntime`, `LocalPersonalRecords`); only their platform presentation is absent.
